● Written to docs/JOINTS.md. One correction to the premise of the request:

  It's 26 keypoints, not 21

  TrackedHand exposes 26 individual Keypoint properties. The "21 hand keypoints"
  figure is the MediaPipe hand model (wrist + 4 × 5 fingers). SIK isn't
  MediaPipe — it adds a <finger>ToWrist keypoint per finger, so it's wrist + 5 ×
  5 = 26.

  Confirmed three independent ways in the source: 26 readonly ... : Keypoint
  declarations on the BaseHand interface (BaseHand.ts), 26 matching fields on
  TrackedHand each assigned from a distinct LandmarkName
  (TrackedHand.ts:100-125, assignments at :232-257), and LandmarkName having
  exactly 26 members. points is built at TrackedHand.ts:818 as wrist + five
  5-element finger arrays.

  Three traps that would have broken inferred names

  Reading rather than guessing was the right call here — the naming is not
  regular:

  The thumb is named differently from every other finger.
  Index/middle/ring/pinky use Knuckle / MidJoint / UpperJoint / Tip for
  landmarks 0/1/2/3. The thumb uses BaseJoint / Knuckle / MidJoint / Tip. So
  thumbKnuckle is THUMB_1 while indexKnuckle is INDEX_0 — the same word maps to
  a different landmark index. There's no thumbUpperJoint and no indexBaseJoint.

  Middle is abbreviated only in the string values. Property middleKnuckle, enum
  MIDDLE_0, but the actual rig string is "mid-0", and WRIST_TO_MIDDLE is
  "wrist_to_mid". Middle is the only abbreviated one.

  <finger>ToWrist isn't a joint on the finger. In Joints.ts the wrist_to_* nodes
  are children of wrist and parents of the finger chain — the metacarpal split.
  All five sit at the wrist end, not distributed along the finger.

  Also worth knowing: getKeypoint() is private (TrackedHand.ts:779), so runtime
  lookup by LandmarkName isn't public API — use the named properties or the
  array accessors.

  Relevance to fingerspelling

  The doc closes with notes for your build, but the one that matters most: M, N,
  S, and T differ mainly by where the thumb crosses relative to the finger 
  knuckles. That distinction lives in thumbTip versus
  indexKnuckle/middleKnuckle/ringKnuckle — so the thumb's off-by-one naming is a
  live hazard in exactly the code that will decide your hardest letters.
  Separately, J and Z are motion letters, not static handshapes; a per-frame
  classifier can't represent them without a temporal buffer.

  Two things about the spec I had to work around rather than implement
  literally.

  The script cannot write templates.json itself

  Lens runtime scripts are sandboxed — there is no filesystem API. I confirmed
  what does exist: global.persistentStorageSystem.store is a GeneralDataStore
  with putString/getString/has/remove only. No file write.

  So the recorder does three things instead:

  - Holds samples in memory as the session runs
  - Mirrors each capture into persistent storage per letter, so a crash, a
    restart, or the operator closing the Lens doesn't lose the run —
    resumePreviousSession picks it back up, dropping any saved sample whose
    width doesn't match FEATURE_DIM
  - Prints the full set to the log between TEMPLATES_BEGIN / TEMPLATES_END, one
    line per sample (TPL|A|0|0.1234,...) plus a TPLMETA| header

  One line per sample rather than one JSON blob is deliberate — a full set is
  ~9,000 floats, which would blow past log line limits as a single string. At
  ~550 chars per line it's safe. Recover with RunAndCollectLogsTool and I'll
  write the file. Pinching after completion re-emits the block, in case the log
  scrolled.

  Pinching with the signing hand would corrupt every sample

  A pinch is a handshape. If the hand forming the letter is also the hand
  pinching to trigger capture, every stored vector is a blend of the target
  letter and a pinch — the data would look plausible and be worthless.

  So the default is two-handed: signingHand (right) forms the letter,
  triggerHand (left) pinches. For one-handed recording, set captureDelaySeconds
  to 2–3 and both hands the same — pinch, release, re-form the letter, capture
  fires on a visible countdown. If the two hands are set the same and the delay
  is 0, it logs a warning at startup rather than silently recording garbage.

  Operator-facing behavior

  The status text carries the letter, a 3 / 5 counter, and which hand to pinch.
  On capture it flashes RECORDED 3/5 for 0.9s, then LETTER COMPLETE before
  advancing. Failures are explicit rather than silent: NO HAND SEEN when the
  signing hand isn't tracked, POSE UNREADABLE when normalization returns null.
  Optional confirmAudio plays a sound on each capture, which matters when the
  operator is watching their hands rather than the panel. A 0.35s cooldown
  swallows accidental double-pinches.

  undoLastSample() and skipLetter() are public so you can wire them to buttons —
  I didn't bind them to gestures, since more gestures on an already two-handed
  rig seemed likelier to cause mis-triggers than to help. Say the word if you'd
  rather have fist-grab mapped to undo.

  Default letters are ABCDEFGHIKLMNOPQRSTUVWXY — 24, omitting J and Z, which are
  motion letters that a per-frame static classifier can't represent.

  Takes the letters map straight out of templates.json, returns 26 Fisher

  landmark is quiet on all three.

● All three fixes are in and compiling. The variance math checks out exactly
  (two-sample analytic case matches to 5 significant figures).

  1. Distinct-frame guarantee

  Every capture now routes through UpdateEvent and is gated on a frame counter
  (there's no getFrameCount() global, so the recorder maintains its own):

  onTriggerPinch()  →  pendingCapture = true       // never captures inline
  onUpdate()        →  frameCounter++
                       if (pendingCapture && frameCounter !== lastCaptureFrame)
  capture()
  capture()         →  lastCaptureFrame = frameCounter

  UpdateEvent fires once per frame and pendingCapture clears before capture()
  runs, so at most one sample per frame — no two samples can ever share a
  frame-cached Keypoint.position. If capture() bails early (untracked,
  degenerate), lastCaptureFrame is deliberately left unchanged, since nothing
  was stored.

  2. Re-form gate

  After each capture the stored vector is retained, and trackReformDistance()
  computes the live pose's Euclidean distance from it every frame. The next
  pinch is rejected until that distance exceeds reformThreshold (default 0.6,
  normalized units). The screen shows live progress — (0.42 / 0.60) — so the
  threshold gets tuned from what real re-forming actually produces rather than
  from my guess.

  undoLastSample() re-arms the gate against the new tail sample; advancing or
  skipping a letter clears it, since there's nothing to re-form away from.
  Turning requireReformBetweenSamples off logs a warning explaining the Fisher
  consequence.

  3. Within-variance warning

  Fires per letter on completion and again as a TPLVAR|letter|n|variance table
  at dump time, with a summary count of suspicious letters.

  One honest limitation on the threshold. 1e-5 catches duplicates and
  near-duplicates, not held poses:

  ┌────────────────────────────────┬──────────┬────────┐
  │              Case              │ Variance │ Result │
  ├────────────────────────────────┼──────────┼────────┤
  │ Identical / same frame         │ 0.0      │ warns  │

  A held pose carrying real sensor jitter sits around 1e-3 — roughly 10× below
  genuine re-forming, but 100× above a "near zero" threshold. So the variance
  check is a backstop against duplication and frame-sharing; the re-form gate is
  what actually prevents held poses. That matches what you asked for ("near
  zero"), but it's worth being explicit that the two mechanisms cover different
  failures rather than the warning being a safety net for the gate.

  The TPLVAR table is what makes this empirical in practice — one letter an
  order of magnitude below its neighbors is visible by eye even when nothing
  trips the absolute threshold. Once real templates land, that table plus
  perLandmarkDiscriminability should tell you whether the recording protocol
  worked before you tune a single threshold.

  Two design points worth calling out:

  Frame caching is deliberate. The jittered vector is computed once per frame
  and reused, so multiple consumers calling getFeatures() in one frame all see
  identical values — the same contract SIK's frame-cached Keypoint.position
  provides. Mock and live behave the same way.

  Randomness is a seeded LCG, never Math.random(). A LEAF scenario replays
  exactly. autoAdvance: false plus manual advanceFrame() gives frame-exact
  control for tests.

  One limitation, stated plainly

  Jitter is added in feature space, after normalization — real tracking noise 
  happens in landmark space, before it. Real noise is correlated across
  dimensions in ways this doesn't reproduce: jitter on the wrist or
  middleKnuckle would in reality rotate and rescale the entire basis, moving
  every other landmark together, whereas here each dimension is perturbed
  independently.

  So this is sound for "does the hold buffer settle under noise of roughly this 
  magnitude" and unsound for "what is my accuracy under tracking noise." A
  threshold tuned only against mock jitter should be treated as provisional
  until a real hand has seen it.

  Related: preserveStructuralDims (default on) leaves dims 0–2 and 36–38
  un-jittered, because normalizeLandmarks can never emit anything but (0,0,0)
  and (0,1,0) there. Without it the mock would emit vectors off the manifold
  real data occupies — and a classifier tuned against those is tuned against
  input it will never see. The test confirms those dims stay pinned while the
  other 72 still receive noise.

  What changed

  Each sample is now {normalized: number[78], raw: number[78]}. Raw is stored

  One thing I changed beyond plumbing: capture() now reads the landmarks once
  via pointsFromTrackedHand and derives both representations from that single
  array, rather than calling normalizeTrackedHand separately. Frame caching
  means two reads would agree in practice, but deriving both from one read makes
  it provable rather than incidental. That required passing mirror explicitly,
  since normalizeTrackedHand was the thing applying it.

  Log format

  Raw and normalized go on separate lines — combined they'd exceed ~1300 chars
  per line, where each alone stays in the 550–800 range and safely inside log
  limits:

  TPL|A|0|<78 normalized>
  TPLRAW|A|0|<78 raw world cm>

  TPLMETA gains rawUnits: "cm_world".

  Two consequences I handled

  A storage-pressure risk. Keeping raw roughly doubles the bytes written to
  persistentStorageSystem, which has a cap. saveLetterToStorage now checks
  getSizeInBytes() against getMaxSizeInBytes() and warns once at 80%, noting
  that the log dump is unaffected. Without this, crash-resume could silently
  stop working mid-session — the exact failure the persistence was there to
  prevent.

  An integration break. MockHandInput.loadFromTemplates indexed
  templates.letters[letter][i] as a bare array. With v2 samples being objects,
  that would have silently fed the mock a garbage features value. Added
  extractNormalized(), which accepts both shapes, so v1 and v2 template files
  both work.

  Resumed pre-v2 samples load fine with raw: null and trigger a warning
  explaining they can't be re-normalized or augmented.

  What this unblocks

  The landmark-space jitter you mentioned is now possible — MockHandInput's
  feature-space jitter can be replaced or supplemented by perturbing the raw

  mock vs live

  classify always takes the full 78-dim vector regardless of mode — reduction
  happens internally, so callers never need to know which variant an instance
  runs. Loading goes through extractNormalized, so v1 and v2 template files both
  work; loadFromJsonAsset(asset) is there since JsonAsset.getString() is how a
  wired-in templates.json reaches script.

  Variants are configured at construction, and buildVariants(file, weights, k)
  returns all four (full+unweighted, full+weighted, reduced+unweighted,
  reduced+weighted) loaded over the same file for side-by-side scoring. The
  transform is applied to templates at load and queries at classify through one
  code path, so the two spaces can't drift apart — a distance computed across
  mismatched feature spaces would be silently meaningless.

  One design decision worth your attention

  The margin is between the best and second-best letter, not the first and 
  second nearest templates. That's not a detail — with several samples per
  letter, the two nearest templates are frequently the same letter, and a
  per-neighbour margin would collapse to zero on exactly the confident cases:

  ┌─────────────────────────────────────┬────────────┐
  │ Query sitting between two A samples │ Confidence │
  ├─────────────────────────────────────┼────────────┤
  │ Per-letter margin (implemented)     │ 0.999 → A  │
  ├─────────────────────────────────────┼────────────┤
  │ Per-neighbour margin (rejected)     │ 0.000      │
  └─────────────────────────────────────┴────────────┘

  So each letter scores as the mean of its k nearest templates (k=1 default),
  and the margin comes from the top two letters. That's the within-class variant
  of k-NN rather than vote-among-k-neighbours, chosen because it makes the
  margin well-defined.

  ├───────────────────────────────────────┼─────────────────────────────────┤

  The limitation you'll need to design around

  Margin confidence cannot reject an unknown pose. The ratio is scale-free — it
  ignores how far the query is from any letter. A hand doing something that
  isn't a letter scored 0.75 confidence at distance 20.0 in the test above: far
  from everything, but much closer to A than to B.

  That's why distance is in the result. Rejecting out-of-vocabulary poses needs
  both gates:

  result.confidence >= minConfidence && result.distance <= maxDistance

  Set both from real recorded data. lastScores() returns the full per-letter
  score vector after each call, which is what you'll want when tuning them.

  module would keep test scaffolding out of production. Small refactor whenever

  How it runs

  After the last letter, the recorder enters a negative phase under _NEGATIVE
  with its own quota (negativeSampleCount, default 30). Same capture path — same
  frame gate, same re-form gate, same {normalized, raw} storage, same
  persistence.

  The display switches to NON-LETTER and cycles a prompt so the operator knows
  what to make. Over 30 samples that lands:

  ┌───────┬──────────────────────────┐
  │ Count │          Prompt          │
  ├───────┼──────────────────────────┤
  │    15 │ MOVE between two letters │
  ├───────┼──────────────────────────┤
  │     3 │ Hand at REST             │
  ├───────┼──────────────────────────┤
  │     3 │ FLAT PALM                │
  ├───────┼──────────────────────────┤
  │     3 │ POINTING                 │
  ├───────┼──────────────────────────┤
  │     3 │ LOOSE FIST               │
  ├───────┼──────────────────────────┤
  │     3 │ Hand MOVING              │
  └───────┴──────────────────────────┘

  50% transitional, weighted deliberately per your point — a hand between two
  letters is a plausible-looking handshape that isn't a letter, which is exactly
  what a distance gate needs to reject. The static poses sit far from
  everything and are the easy case.

  The re-form gate does useful work here too: it forces each negative to differ
  from the last, so the operator can't pinch 30 times at rest.

  Exclusion from classification

  Classifier.loadTemplates now skips any key starting with _ before it becomes a
  candidate — without that, "not a letter" would be a possible classification
  answer. It logs what it excluded and how many calibration samples it saw.
  MockHandInput.loadFromTemplates also skips reserved keys unless you name them
  explicitly in options.letters, since replaying negatives to test rejection is
  legitimate.

  Verified: letterKeys returns ["A","B"] from a file containing A, B, _NEGATIVE,
  _SCRATCH.

  One implementation detail that would have been a silent bug: parseLetters
  splits its input into single characters, so routing _NEGATIVE through it
  yields ["_","N","E","G","T","I","V"]. It's appended after parsing instead,
  with a comment saying why.

  A diversity check that needs no magic number

  Negatives are deliberately dissimilar poses, so they should vary more than
  repeats of a single letter. At dump time the recorder compares negative
  within-set variance against the mean within-letter variance and warns if
  negatives don't exceed it:

  TPLNEG|30|<negative variance>|meanLetterVar=<letters' mean>

  The letters supply the reference, so there's no guessed threshold. If it
  trips, the negatives were captured too uniformly and would under-estimate how
  close a non-letter can get — yielding a maxDistance that's too tight.

  One piece of plumbing

  NEGATIVE_KEY is needed by both the recorder and the classifier, and the
  template-schema types were living in MockHandInput.ts — the coupling I flagged
  earlier, about to gain a third importer. I moved the schema (TemplateSample,
  TemplatesFile, extractNormalized, plus extractRaw, letterKeys,
  negativeSamples) into Assets/Scripts/TemplateFormat.ts. MockHandInput
  re-exports the old names, so nothing that imported them broke.

  What's still missing

  The data now exists; measuring the separation doesn't. Setting maxDistance
  means computing letter distances (leave-one-out, so a template isn't scored
  against itself) and negative distances, then finding where the two
  distributions separate. That's a real piece of work with methodology choices
  worth deciding deliberately — I didn't guess at an API for it. Say the word
  and it's the next thing.

  Wrong-letter handling

  A wrong commit does three things and avoids two:

  - Emits onWrongLetter with {signed, expected, index, mistakesOnCurrentLetter}
    — the UI can say "you signed E, expected L"
  - Enters wrong status for wrongDisplaySeconds (default 1.2s), carrying
    wrongLetter in the state
  - Clears itself back to signing, still expecting the same letter

  It does not advance the index, and does not reset the phrase. Verified: after
  signing E for L, index stayed at 1, progress stayed at 0.25 (the completed C
  survives), and after 1.1s status returned to signing still expecting L.

  One deliberate choice: a correct commit during the wrong-flash is accepted 
  immediately and clears it. The flash is feedback, never a lockout — verified
  returning correct mid-flash with the index advancing.

  mistakesOnCurrentLetter resets on a correct letter while the phrase total
  persists (2 → 0, total stays 2). That's exposed rather than acted on, so the
  UI decides what escalating help looks like instead of the state machine
  inventing it.

  State for the UI

  getState() returns letterStatus[] — one entry per character, each pending | 
  current | done | skipped | unsignable — so the word renders with per-letter
  progress rather than just an index. Plus progress, mistakes, skipped,
  phraseIndex/phraseCount.

  Events: onCorrectLetter, onWrongLetter, onWrongCleared, onPhraseComplete,
  onPhraseChanged, onLetterSkipped — using SIK's Event<T>, matching the
  project's convention.

  Two demo-safety additions

  J/Z guard. J and Z are motion letters that a static classifier can't produce,
  and they're excluded from the recorder's default set. A phrase containing one
  would be silently unfinishable — a live-demo dead end with no explanation.
  setAvailableLetters(classifier.loadedLetters()) makes setPhrase refuse such a
  phrase, log which letters are missing, and park rather than pretend.
  signablePhrases() filters the menu. Verified: JAZZ reports ["J","Z"] and is
  refused; the menu narrows to ["CLAD"].

  skipCurrentLetter(). If a letter simply won't classify on the day, the demo
  can move on. Counted as skipped, explicitly not a mistake. Beyond your literal
  ask, but a stuck letter with no escape is the failure mode most likely to
  bite during a live run — say the word and I'll drop it.

  Spaces auto-skip: "AB CD" marks index 2 unsignable and jumps straight from B
  to C.

  Preset menu

  Two implementation choices worth knowing

  The target word is one rich-text Text, not N character slots. enableRichText
  plus per-character <color=#rrggbb> markup means one assignment repaints the
  whole word. Per-character slots would need pre-allocation, and disabling
  unused ones drops them out of the layout pass while leaving them reserves
  width.

  The bar is a BackPlate width, not a colored glyph run. I checked: BackPlate
  exposes no tint — only style: "default" | "dark" | "simple" — so the bar gets
  contrast from two plates in different styles, and grows continuously via
  size.x. A block-glyph text bar would have been colorable but depends on glyph
  coverage in the system font and renders as tofu when it's missing. Semantic
  color therefore lives on the Text elements, which do expose textFill.color.

  Three things I decided rather than followed

  No IK / interactor coverage. The skill asks for an IK reachability scenario on
  reach-sensitive UI. This Lens has no interactables at all — no buttons,
  sliders, or draggables — so DefaultLeafInteractor, LeafHandInteractor and
  createIKInteractor have nothing to reach for. Writing one would have meant
  inventing a control that doesn't exist, which the skill also forbids. Worth
  revisiting the moment you add a phrase-menu button.

  Frame-based waits, not sleep(). HoldBuffer counts frames and preview frame
  rate isn't fixed, so sleep(600) would be flakiest in exactly the tests that
  care about window length. waitUntil(predicate, maxFrames) and frames(n) step
  with nextFrame().

  How low confidence is manufactured. Rather than hoping heavy jitter lands
  between two letters, the scenario blends the target 50/50 with its nearest
  neighbour — that sits equidistant by construction, so 1 - d_best/d_runnerUp
  collapses deterministically. Same for the rejected frame: the pose is scaled
  off-manifold while the structurally-constant dims are preserved, so it stays a
  well-formed vector that simply fails the distance gate.

  I added a test surface to SignBridge

  Read-only state (getPhraseState, getHoldState, getView, isReady,
  getLoadedLetters, distanceBetween, nearestOtherDistance) plus
  playScript(steps) and setMaxDistance(). The skill says don't modify the Lens
  to make tests work — I read that as "don't rename objects to fix lookups", and
  this changes no behavior. But it is a real addition, so flagging it rather
  than burying it.
